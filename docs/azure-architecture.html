    The big ideas

    Your Mac is out of the picture

    Before, the backend, verifier and a temporary tunnel ran on your laptop. Now all three jobs are done in Azure at one permanent address.

    Keys stay in one locked place

    The phone never holds keys. It just forwards the chip’s encrypted link. Only the verifier, reading from Key Vault, can decrypt it.

    Three anti-cheat checks

    1) A forged or edited link fails decryption. 2) Every tap has a higher read number, so old links are refused. 3) A retry with the same request ID never adds a second stamp.

    Code never “moves into” Azure by hand

    Code lives in GitHub. A build packages it and Azure runs the package. Merging to main is the deploy button.

    Badges instead of passwords

    The app and GitHub prove who they are with Azure managed identities, so no database password or deploy password exists to leak.

    Still a prototype

    Anonymous “guest” cards (no sign-in yet) and factory test keys on the chips. Before real customers: turn prototype mode off, connect real accounts, program chips with real keys.

      The Dockerfile, in plain English

      A Dockerfile is the recipe for an image. Ours has two stages: a big “kitchen” that compiles the code, and a small “serving tray” that is all that ships.

      # STAGE 1: the kitchen (has the .NET compiler, thrown away afterwards)
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
COPY services/api-dotnet/Joeyy.Api/Joeyy.Api.csproj ...      # 1. the shopping list first
RUN dotnet restore ...                                   # 2. download packages (cached if the list didn't change)
COPY services/api-dotnet/Joeyy.Api/ ...                       # 3. then the actual code
COPY services/api/db/migrations/ ...                          # 4. the SQL files, shared with Node
RUN dotnet publish ... -o /app                           # 5. compile into /app, and check migration 0005 is there

# STAGE 2: the serving tray (small; only the runtime, no compiler)
FROM mcr.microsoft.com/dotnet/aspnet:10.0
RUN apt-get install fonts-dejavu-core ...                # 6. a font, so cafe names can be drawn on the Wallet card
COPY --from=build /app .                                 # 7. take only the finished program from the kitchen
ENV HOST=0.0.0.0 PORT=8080                               # 8. listen on every address inside the container, port 8080
USER $APP_UID                                            # 9. run as a normal user, not root
ENTRYPOINT ["dotnet", "Joeyy.Api.dll"]                   # 10. what starts when the container starts

      Why the build starts at the repo root

      The migrations live in services/api/, outside services/api-dotnet/. A build can only copy files from inside its starting folder, so it starts at the top of the repo. .dockerignore then keeps everything else out.

      Why “packages first, code second”

      On a laptop, Docker remembers each step: if only your C# changed, the package download is reused and the rebuild is quick. Azure’s cloud build starts fresh every time, so there it just keeps the recipe tidy.

      Why it shrinks the image

      The compiler is only needed to build, so it is left behind. Only the finished program plus the runtime ships, about 270 MB in total.

      A deploy, step by step (today)

      1. You commit. infra/deploy.sh refuses to run if services/api/, services/api-dotnet/ or infra/ have uncommitted changes, so what runs always matches a commit.
      2. Azure builds the image. az acr build uploads the repo and runs the Dockerfile inside Azure, so Docker isn’t needed on your Mac. Result: joeyy-api-dotnet:<commit> and joeyy-verifier:<commit> on the registry shelf.
      3. The app is told the new tag. az deployment group create with infra/app.bicep and dev.bicepparam creates a new revision.
      4. Azure starts it, tests it, switches. The new revision must pass the startup probe on /healthz. Only then does it get 100% of the traffic and the old one is shut down. If the new one never becomes healthy, the old one keeps serving.
      5. The script confirms. It polls /api/v1/healthz until it says ok and prints “Live”.
      Not part of a deploy: database changes. New SQL files are applied by a person with dotnet Joeyy.Api.dll migrate (or npm run migrate) before deploying code that needs them.
      Going back to Node: the last Node image is joeyy-api:72959913a272. One command puts it back in a few minutes; it is written in infra/README.md under “Going back to the Node backend”.

      Known limits and things to watch

      Rate limits may be shared by everyone

      The limits (120 requests a minute; 10 guest or sign-in starts per 15 minutes) count by the caller’s connection address. Behind Azure’s front door that address is probably Azure’s own proxy, not each phone, so all phones may share one allowance. Node behaved the same. Not yet checked. Fine for a few testers; to fix before real customers.

      One copy on purpose

      One replica keeps the rate limit simple and the worker predictable. The worker’s database locks mean two copies wouldn’t double-send pushes, but the limits would then be per copy.

      Partner side isn’t here

      Business setup, image uploads and OIDC sign-in still exist only in the Node code. On the live api, /v1/partner/… now answers “no such route”.

      Pass images drawn differently

      Node drew the strip with sharp; .NET draws it with SkiaSharp. Same layout and sizes, but tiny pixel differences in the circles and text are possible.

      Still a prototype

      Anonymous guest cards (each phone has its own card) and factory test keys on the chips. Real accounts, real chip keys and a prod environment are still ahead.
